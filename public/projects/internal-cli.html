Internal CLI

A single onboarding-to-deploy CLI that replaced a wiki page of copy-pasted shell commands.

New engineers spent their first week running commands copied from a wiki page that was out of date as often as not. I built a single CLI covering environment setup, local services and deploys, versioned alongside the infrastructure it drove so it could never drift from what the wiki described.

Problem

The wiki page was the build system

Getting set up to work on the checkout service took a new engineer the better part of a day, spent copying thirty-one commands out of a page nobody owned and everybody edited. The page was not wrong so much as partly right: some of it described the infrastructure as it had been eighteen months earlier, and there was no way to tell which parts by reading it.

What a wiki page cannot do

  • Fail. A stale command runs perfectly well and leaves you with the wrong environment.
  • Tell you which of its steps you have already done, or which you can skip.
  • Change when the infrastructure it describes changes — it lived in a different system, edited by different people, on a different week.
  • Say which version of itself you followed, when you ask for help two hours later.

Approach

Stop writing the steps down and run them

The instructions were already a program. They were just being executed by a person, slowly, with no error handling. I moved them into one binary and put it in the same repository as the Terraform and Helm charts it drives, so that changing the infrastructure and changing the command that sets it up is one commit and one review — and neither can be done without the other.

Why Rust, honestly

Not for the speed — it is a program that shells out and waits. It was a single static binary with nothing to install first, which mattered more than anything else about it: the whole point was to avoid asking somebody to set up a runtime before they could set anything else up. Any language that produced one would have done, and Go nearly did.

Result

One command instead of a wiki page

Time to a first local build for a new engineer went from roughly a day of following stale instructions to under twenty minutes, and the tool itself became the source of truth the wiki page used to be.

The subcommand I did not plan was the one that got it adopted: dev doctor, which checks the environment and names the assumption that is broken. It turned every "it doesn't work on my machine" from a conversation into a paste. Five other teams asked for the tool in the first quarter; the sixth added support for their own stack and sent it back.
