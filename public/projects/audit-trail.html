Audit Trail

A hash-linked record of every privileged action, cheap enough to write on the hot path and hard enough to argue with in an audit.

On this page Problem Approach Result

Access logs lived in three systems, none of which could prove they had not been edited. I replaced them with one append-only table where every record carries the hash of the record before it, and a daily seal anchors the chain — which turns "who changed this?" from an investigation into a query.

Problem

Three logs, no answers

Privileged actions were logged by whichever service happened to perform them: the admin API wrote rows, the support tool wrote to a file, and the data platform wrote nothing at all. Reconstructing a single incident meant three exports, three clock skews and a spreadsheet.

What an auditor actually asked for

  • Every action against a customer record, in one place, in order.
  • Evidence that nothing had been removed from that list after the fact.
  • A retention story that did not depend on anyone remembering to run something.

Approach

Make deletion as loud as editing

Every record stores the hash of its own contents and the hash of the record before it. Editing a row breaks the chain from that point on; deleting one breaks it too. Neither is prevented — the database can always be written to — but neither can happen quietly, which is the property an audit actually needs.

Why not a ledger database

We costed one. It solved the tamper-evidence problem we had and introduced an operational surface nobody on the team knew how to run at 3am. A column in the database we already operate was the cheaper trade, and it is the trade I would make again.

Result

The question became a query

Verification walks the chain and takes about eleven seconds over a year of records, which is fast enough that it runs nightly rather than on request. The first run found no tampering and two application bugs writing records with the wrong subject — which was worth the whole project on its own.
