Event Pipeline

Replacing a nightly batch job with an append-only event log that any team can read from, replay and reason about.

Role
Lead backend developer
Team
4 engineers
Status
In production
Stack
Kotlin · Kafka · PostgreSQL · Kubernetes

A retail platform where the reporting, search and partner integrations all depended on a single nightly batch job. It had grown to seven hours, and any failure inside it meant a day of stale data across the whole product. I led the rewrite to an append-only event log: one write path, independent readers, and offsets that make replay a routine operation instead of an incident.

Problem

The nightly batch had run out of night

Every downstream system read from the same nightly job. It pulled the day's rows out of the operational database, transformed them, and pushed the results into the warehouse, the search index and a set of partner webhooks. When it was written it took forty minutes. By the time I picked it up it took a little over seven hours, and it had started colliding with the start of the European trading day.

The failure mode was the part that actually hurt. The job was one transaction-shaped unit of work with no checkpoints, so a timeout in the last step threw away the previous six hours. Reruns were manual, they ran during business hours, and they doubled the load on the same database the storefront was serving from. Twice that quarter partners received the previous day's prices.

What was actually broken

  • One shared failure domain: a slow search index could delay warehouse reporting by a full day.
  • No way to reprocess a subset. Fixing one bad transform meant rerunning everything.
  • Backfills competed with production traffic, because there was only one copy of the data.
  • Nobody could answer "what did we know at 14:00 yesterday?" — the job overwrote its own inputs.

We did not have a performance problem. We had a coupling problem that happened to show up as a performance problem.

From the design review that started the rewrite

Approach

One append-only log, many independent readers

The core decision was to stop moving data and start publishing facts. Services write immutable events to a partitioned log as things happen. Every consumer reads that log at its own pace and keeps its own offset, so a slow or broken reader falls behind on its own rather than holding up anyone else.

That only works if writers cannot corrupt the log and readers can safely see the same event twice. Both are solved at the edges rather than in the middle: a single ingest service validates every event against a schema registry before it is accepted, and every consumer is written to be idempotent on a deterministic key. The log itself stays boring.

The decisions that mattered

  1. Partition by tenant, not by event type. Ordering guarantees are only useful where causality actually exists, and all of ours was per-tenant.
  2. At-least-once delivery plus idempotent consumers, instead of chasing exactly-once. Cheaper to operate and far easier to explain during an incident.
  3. Schema validation at ingest, with backward-compatible evolution enforced in CI. A producer cannot deploy a breaking change.
  4. Seven days of retention on the raw topics. Long enough for every realistic replay, short enough to stay affordable.

The claim table is the whole trick. It is a narrow table with one unique index, it lives in the consumer's own database rather than a shared one, and rows are pruned on the same schedule as the topic retention. It costs one extra write per event and it removes an entire category of duplicate-processing bugs.

Operations

Replay had to be routine, not heroic

A pipeline that can only move forward is a pipeline you are afraid of. The point of keeping offsets per consumer is that reprocessing becomes a normal operation: pick a consumer, pick a point in time, let it catch up. No database restore, no coordination with other teams, no maintenance window.

The part I got wrong first

The first version paused the whole fan-out worker when any single sink failed, because that seemed safer. It was not: a partner webhook being down stopped the warehouse from getting data, which is exactly the coupling we were trying to remove. Circuit breakers moved to per-sink, and the blast radius went with them.

Freshness went from a nightly cycle to just over a second at the ninety-ninth percentile, and it stayed there through two Black Fridays. The number I care about more is the second one: since the cutover there has not been a single incident caused by downstream systems disagreeing about the state of the world. That class of bug is gone, not reduced.

The migration itself ran both systems side by side for six weeks with a continuous diff between the two outputs. It surfaced eleven genuine discrepancies, nine of which turned out to be pre-existing bugs in the batch job that nobody had noticed. Cutover was a configuration change, and the batch job was deleted a month later.

What I would do differently

  • Introduce the schema registry first, as its own project. Retrofitting it while the pipeline was in flight cost us three weeks.
  • Write the replay tooling before the consumers, not after. We hand-rolled offset resets for the first two months and it made people nervous about using them.
  • Be stricter about payload size early. A handful of producers embedded documents that belonged behind a reference, and splitting them out later was tedious.
