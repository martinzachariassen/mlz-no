Tenant Isolation

Moving a shared-everything multi-tenant platform onto per-tenant pools, so one customer's bad afternoon stops being everyone's.

Role
Backend developer
Team
3 engineers
Status
In production
Stack
Kotlin · PostgreSQL · Kubernetes

Every tenant shared one connection pool, one worker fleet and one rate limit, so a single customer running a bulk import could push the whole platform past its latency objective. I introduced a tenant resolution step at the edge and moved the blast radius from the platform to the pool.

Problem

One tenant, everyone's outage

The platform was shared-everything, which had been exactly right when it had eleven customers and was increasingly wrong at four hundred. Capacity was provisioned for the aggregate, and the aggregate was dominated by whoever happened to be doing something unusual that afternoon.

We were not over capacity. We were over capacity for ninety seconds a day, in a different place each time.

From the postmortem that funded the work

What shared-everything actually cost us

  • A bulk import from one tenant exhausted the connection pool for all of them.
  • Rate limits were global, so protecting the platform meant throttling innocent traffic.
  • Two enterprise deals stalled on a question about key separation that we could not answer honestly.
  • Capacity planning was a single number nobody could attribute to anything.

Approach

Resolve the tenant once, at the edge

Every request already carried a tenant identifier; nothing downstream did anything with it. The change was to resolve it exactly once, at the edge, into the three things that had been global — which pool serves this tenant, what quota it has, and which key its data is encrypted with — and to make every component below that point single-tenant by construction.

The decisions that mattered

  1. Pools, not databases. Physical separation per tenant was unaffordable at four hundred; a pool of tenants sized to a known worst case was not.
  2. Quota at the edge, enforced before the work is queued. Throttling after a request has taken a connection defeats the point.
  3. Dedicated pools as a product tier rather than an exception, so the two tenants who needed one stopped being a special case in the code.
  4. Migration one pool at a time, with the router able to send a tenant back to the shared fleet on a config change.

The part I got wrong first

The first resolver hit the database on every request and cached nothing, on the theory that tenant configuration changes should take effect immediately. It added 6 ms to the p50 of every call on the platform. A sixty-second cache with an explicit invalidation on publish gave back all of it and nobody has ever noticed the delay.

Result

The blast radius has a name now

p99 during a saturated pool
84 ms
Pools affected by the worst incident
1 of 17
Resolver cost after caching
6 ms → 0
Enterprise deals unblocked
2

The number I care about is the second one. Incidents did not stop — a tenant can still saturate the pool it sits in — but an incident now has a boundary you can name in the first minute, and the other sixteen pools carry on without anybody paging them.

The unplanned benefit was capacity planning. Cost and load are attributable per pool, and per pool means per tenant, which turned a single unexplainable infrastructure line into a number the commercial side could actually use.
